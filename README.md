# BeatLooker · 最小验证

桌面端网页：**从麦克风或本地音频文件拿声音，画上下两张同步的图**。

上面是**频谱图**：

- **X 轴 = 时间**（从右往左滚动）
- **Y 轴 = 频率**（对数轴，低频在下、高频在上）
- **每个格子的颜色 = 该频率在该时刻的能量大小**

下面是**能量图**（总能量随时间的变化）：

- **X 轴 = 时间**，与上图共用同一条轴、同一个滚动位置
- **Y 轴 = 总能量**，范围 **0 到无穷**，满量程自适应
- 柱子从面板底部往上填充，顶端一条亮线标出当前值

两张图可以整体延迟 N 秒显示（默认 **1 秒**）。

页面下方还有**能量记录**：把每个读数连时间轴一起存下来，再按你输入的速度和拍号
排成一行行（每行若干小节），用来对照歌曲结构。见「能量记录与谱面视图」。

音源有两种：**麦克风实时采集**，或**直接加载本地音频文件**（mp3 / wav / m4a /
ogg / flac …，见「从本地音频文件读取」）。

## 运行

**方式一：双击 `start-dev.bat`（推荐）**

**默认就是局域网模式**——因为双击 .bat 没法传参数，默认必须是手机能用的那个。
它会自动完成：检查 Node → 缺依赖就装 → 在独立窗口起 dev server →
轮询确认服务真的应答了 → 查出局域网 IP → 打印完整网址 → 打开浏览器。
失败时会把原因打在窗口里并 `pause` 住，不会一闪而过。

只想在电脑上用（不要自签名证书那个警告）：

```cmd
start-dev.bat local
```

端口默认 5173，被占用时可以临时换一个：

```cmd
set PORT=5199
start-dev.bat
```

**方式二：手动敲命令**

Win11 上用 **CMD**（PowerShell 默认策略是 `Restricted`，直接敲 `npm` 会被
`npm.ps1` 挡下；要么用 CMD，要么在 PowerShell 里写 `npm.cmd`）：

```cmd
cd /d D:\beatlooker
npm run dev        :: 只有本机，http
npm run dev:lan    :: 局域网 + https，手机可用
```

打开 http://localhost:5173 ，点「开始」，允许麦克风权限。

> 必须走 `localhost`（或 HTTPS）。`localhost` 属于安全上下文，
> `getUserMedia` 才可用；直接双击用 `file://` 打开拿不到 `navigator.mediaDevices`。

### 让局域网里的手机也能打开

```cmd
start-dev.bat
```

（这就是默认行为。手动的话是 `npm run dev:lan`。）

局域网模式相比本机模式做了三件事：**打开 HTTPS**（自签名证书）、**监听所有网卡**
（`::`，Windows 双栈下同时收 IPv4）、**放开 Vite 的 Host 校验**。

启动脚本会自己查出局域网 IP 并把完整网址打出来，不用再去 dev server 窗口里找：

```
  Ready.

  ============================================================
    Phone / LAN   :  https://192.168.2.250:5173/
    This computer :  https://localhost:5173/
    Also try      :  https://172.30.252.132:5173/
  ============================================================

  On the phone: open the Phone / LAN address above. Same Wi-Fi required.
  The certificate is self-signed - tap Advanced / Proceed to continue.
  You MUST use https on the phone: plain http blocks the microphone.
```

手机连同一个 Wi-Fi，直接访问 **Phone / LAN** 那一行。第一次会提示证书不受信任，
点「高级」→「继续前往」即可继续。

**那个 IP 是怎么挑的**：`Get-NetIPAddress` 会列出所有网卡，包括 VPN 的虚拟网卡。
脚本按 `192.168.x` → `10.x` → `172.16-31.x` → 其它 排序，第一条作为主地址
（家庭/办公 Wi-Fi 通常就是这一条），其余的列在 `Also try` 里备用 —— 万一主地址
连不上（比如 VPN 抢了路由），换一条试。手动模式（`npm run dev:lan`）没有这个排版，
看 dev server 窗口里的 `Network:` 行即可。

#### 为什么局域网必须走 HTTPS

手机用 `http://192.168.x.x` 打开时**不算「安全上下文」**，浏览器会直接禁掉
`navigator.mediaDevices` —— 表现是点「开始」毫无反应，或者提示「拿不到麦克风接口」。
这不是代码问题，是浏览器的硬性安全策略。

顺带一提：**加载本地音频文件不受这个限制**，纯 HTTP 下也能正常用（解码和分析都不需要
安全上下文），只有麦克风需要。

#### 连不上时先看「绑定地址」

这是最容易搞错、也最容易验证的一点。在本机跑：

```powershell
Get-NetTCPConnection -State Listen | Where-Object { $_.LocalPort -eq 5173 } | Select-Object LocalAddress
```

| 结果 | 含义 |
|---|---|
| `::` 或 `0.0.0.0` | 监听所有网卡 ✓ 手机能连 |
| `::1` 或 `127.0.0.1` | **只有本机** ✗ 手机连不上，说明跑的是本机模式 |

**注意别用「在电脑上访问自己的局域网 IP」来验证局域网是否可用** —— 本机访问自己的
IP 走的是自环路径，不经过防火墙入站过滤，通了也证明不了外面能连进来。

#### 手机上的两个坑

- **iOS 更严格**：iOS Safari 对自签名证书不放过。如果一直弹不出麦克风权限，
  需要在 设置 → 通用 → 关于本机 → 证书信任设置 里信任该证书。
- **兜底方案**：自签名证书在手机上实在搞不定的话，用内网穿透拿一个真实域名 +
  可信证书，麦克风就能正常工作：

  ```cmd
  npx localtunnel --port 5173
  ```

  或者用 cloudflared / ngrok 之类的隧道工具。

#### 默认模式就是局域网模式

因为**双击 .bat 没法传参数**，默认必须是手机能用的那个 —— 否则双击出来的服务只监听
`::1`，手机怎么都连不上（这个坑真实踩过，表现是「手机访问不了」）。代价是桌面浏览器
每次会提示一次证书不受信任。

不想吃这个麻烦就用 `start-dev.bat local` 切成纯 HTTP + 只听 localhost。
`npm run dev` 也仍然是本机模式，给不想看到证书警告的场景用。

## 从本地音频文件读取

除了麦克风，也可以直接加载本地音频文件分析。两种音源互斥：加载文件会先停掉麦克风。

- 点「选择音频文件」，或者**把文件直接拖到频谱图上**
- 解码用浏览器内置的 `decodeAudioData`，**不引第三方解码库**
- 分析是离线一次算完的（带进度条），不用等歌播完

### 支持哪些格式

取决于浏览器，通常能吃 **mp3 / wav / m4a(aac) / ogg / opus / flac / webm**。
Chrome 和 Firefox 覆盖最全，Safari 对 ogg 支持有限。解码失败会给出明确提示，
不会静默失败。

解码走 `OfflineAudioContext` 并统一重采样到 48kHz —— 不受声卡实际采样率影响，
否则同一个文件在不同机器上时间轴会不一样。

### 文件模式下面画什么

实时模式是「滚动最近几秒」，文件模式是「整首歌铺在一屏上」：

- 上半：**整曲频谱图**。原始列数很多（40 秒就有 3747 列），存的时候压到最多
  4096 列，逐行取**最大值** —— 用平均值会把瞬态削平
- 下半：**整曲能量曲线**，横轴是整首歌
- 粉色竖线是播放头，跟着下面的播放器走
- 下方「谱面」照常工作：文件分析出的读数直接喂给它，输入 BPM 和拍号就能按小节排开

### 存的是什么，占多少

频谱栅格**存 dB 字节而不是颜色**：颜色里已经把灵敏度烘进去了，之后一改灵敏度
整首歌就得重新分析；存 dB 则可以在显示时再套，改灵敏度只是重画一遍。

| 项目 | 占用 | 说明 |
|---|---|---|
| 能量读数 | 4 字节/读数，约 **45 KB/分钟** | 和录制模式同一套存储 |
| 频谱栅格 | 最多 4096 x 360 字节 ≈ **1.4 MB** | 歌再长也不涨（超出就压缩） |
| 解码出的 PCM | 约 **11 MB/分钟**（单声道） | 分析完即可回收，但是峰值内存的大头 |

最后一行值得留意：一首 5 分钟的立体声歌，解码后的 AudioBuffer 约 115 MB，
再混成单声道又是 58 MB，分析期间峰值接近 170 MB。这是浏览器解码的固有代价，
不是这份代码额外占的。

## 数据流

```
麦克风
  └─ MediaStreamAudioSourceNode
       └─ AudioWorkletNode (public/wave-worklet.js)
            │  每 2048 个原始样本 postMessage 一批到主线程
            ▼
        DelayLine 环形缓冲（保留 4 秒原始音频）
            │  每积累 512 个样本（hop），取一个窗口做 FFT
            │  窗口结尾 = 最新样本往前 delaySamples 个  ← 延迟发生在这里
            ▼
        SpectrumAnalyser（汉宁窗 + FFT + 单边幅度谱，1024 个 bin）
            │  一列 1024 个幅度值
            │  同时算一次 columnEnergy() = Σ 幅度²，也就是这一列的总能量
            ▼
        Spectrogram 列环形缓冲
            │  渲染每帧取走还没画的列
            ▼
        画布最右侧：一列 2x560 像素（两个面板共用这一列）
            │  上半 0..347 行  频谱图：每行颜色 = 该频率段的平均能量
            │  中间 347..357 行 空隙 + 一条分隔线
            │  下半 357..560 行 能量图：从底部往上填到「总能量 / 满量程」
            ▼
        整块画布向左平移 2 像素，给下一列腾位置（两张图一起移）
```

### 参数与取舍

| 参数 | 值 | 含义 |
|---|---|---|
| `FFT_SIZE` | 2048 | 频率分辨率 ≈ 23.4 Hz/bin（48kHz），窗口时长 ≈ 43 ms |
| `HOP` | 512 | 时间分辨率 ≈ 10.7 ms 一列，即约 94 列/秒 |
| `COL_W` | 2 CSS px | 一列的宽度；实际按 `COL_W × dpr` 换算成设备像素 |
| `F_MIN` / `F_MAX` | 50 / 16000 Hz | 对数频率轴的上下限 |

时间跨度 = `画布宽度 / COL_W / 列每秒`，约 **4~5 秒**（取决于窗口宽度和采样率），
界面右上角的 HUD 会实时显示当前跨度。

### 延迟是怎么做的

延迟**不是**在界面上等 1 秒，而是把原始音频存进环形缓冲，取 FFT 窗口时
把读取位置往回挪 `delaySeconds × sampleRate` 个样本。延迟量按**样本数**计算，
所以精确到样本，不受渲染帧率影响。`src/lib/delayLine.ts` 是纯计算模块，可以单测。

### 两张图为什么天然同步

不是「分别画两张再想办法对齐」，而是**同一列数据、同一个 x，一次性写进同一张
ImageData**：上半段用 `renderColumn()` 写频谱，下半段用 `renderEnergyColumn()` 写能量，
中间的缝隙用 `fillRows()` 填掉；滚动时整块画布一起 `drawImage(-2, 0)`。
所以两张图不存在「漂移」这种可能 —— 它们本来就是同一列像素。

### 能量图的纵轴：0 到无穷怎么画

总能量是 Σ|X[k]|²，恒 ≥ 0 且**没有上界**，所以纵轴不能写死一个最大值。做法是
自适应满量程：

- **瞬时上抬**：出现更大的能量就立刻把满量程抬上去，绝不裁掉数据
- **按时间常数回落**：`energyMax *= exp(-dt / 3)`，峰值过去后约 3 秒收回来

纵轴顶端和中间的刻度值直接标在面板上，随时能看到当前满量程是多少。中间那个刻度
不是简单的一半，而是用 `valueAtLevel()` 反推出来的，所以三档刻度下标得都对。

**但线性刻度实测不好用。** 拿 120BPM 的鼓点 + 和声（3000 个读数）量了一下：

| 分位 | 能量/满量程 | 线性高度(48px) | 平方根 | dB(60dB) |
|---|---|---|---|---|
| 中位数 | 3.25% | **1.5 px** | 8.5 px | **23.7 px** |
| 90% | 4.19% | 2.0 px | 9.6 px | 25.4 px |
| 99% | 62.8% | 29.5 px | 37.2 px | 43.8 px |

线性刻度下 90% 的时间曲线都贴在基线 2 像素以内，等于看不见。所以界面给了
「能量纵轴刻度」三档，**默认 dB**：线性（严格 0 到无穷）、平方根、dB（相对满量程
60dB）。三种都满足 0 能量 → 0 高度且单调递增，只是弱音抬高的程度不同。

## 能量记录与谱面视图

页面分为「实时」和「记录」两部分，它们的存储策略完全不同：

- **实时**只保留屏幕上能看到的那几秒（环形缓冲，画完就丢）
- **记录**从点「开始」那一刻起，每个读数都按顺序存下来，停麦也不丢

### 存了什么

只存读数本身（Float32），**时间轴不单独存**：读数等间隔产出，第 i 个读数的时间
就是 `i / rate` 秒，其中 `rate = 采样率 / hop ≈ 93.75/秒`。这样省掉一半空间，
更重要的是时间轴不可能和读数错位。开销：

| 时长 | 读数个数 | 占用 |
|---|---|---|
| 2 分钟 | 11,250 | 45 KB |
| 10 分钟 | 56,250 | 225 KB |
| 1 小时（默认上限） | 337,500 | 1.35 MB |

分块存储（默认 4096 个读数一块），避免单个大数组反复扩容时的整块拷贝。

### 记录挂在「产出」而不是「渲染」

这一点很关键。渲染会因为切后台、长时间卡顿而丢弃列（见下面「切后台会落后」），
如果跟着渲染记录，时间轴就会出现空洞，`i / rate` 这个关系立刻失效。
所以记录挂在引擎产出那一列的时刻：**每个 hop 恰好一个读数，不多也不少**。

### 谱面怎么排

输入速度（BPM）、拍号（分子/分母）、每行小节数，然后：

```
每拍秒数   = 60 / bpm                ← BPM 按拍号分母的时值计
每小节秒数 = 拍号分子 * 每拍秒数
每行秒数   = 每行小节数 * 每小节秒数
每行读数数 = 每行秒数 * rate         ← 可以是小数，不取整
```

行边界一律用 `round(row * readingsPerRow)` 现算，而不是逐行累加整数 —— 否则行号
一大就会累积舍入误差，几百行之后整张谱面会偏掉。自检里有一条断言专门盯这个：连排
2000 行，每行起点必须严丝合缝等于上一行终点，且累计偏差 < 0.5 个读数。

BPM 按分母计是有意选的：这样 4/4、3/4、2/4 下「120」都表示每拍 0.5 秒，符合大多数
人打拍子的直觉；6/8 下 BPM 指的就是八分音符。界面会实时显示推导出来的「每小节 x 秒 /
每拍 x 秒」，一眼就能看出对不对。

### 画法

所有行共用同一个满量程（记录的历史最大值），所以行与行之间的高低可以直接对比。
每个像素列取该列覆盖范围内读数的**最大值**而不是平均值 —— 缩得太小时平均值会把瞬态
削平，而看这种图要的正是峰值。亮线是小节线，暗线是拍线，每行左侧标注小节号和起始时间。

谱面最多画 `ROW_CAP = 96` 行（96 行在 900px 宽下约 16MB 画布）。记录超过 96 行时
数据仍在内存里，只是没画出来，加大「每行小节数」或调大 `ROW_CAP` 即可。

## 前 3 小节节奏（简谱 + 五线谱）

页面最下方可以输入**前 3 小节的节奏**，校验它和拍号对不对得上，并把结果**同时**画成
五线谱和简谱。

只输**时值**、不输音高，所以渲染时所有音符落在同一条线上 —— 这正是「节奏谱」的常见
形态；简谱那边统一用 `1` 表示音符、`0` 表示休止符。

### 怎么操作

- 上面三个按钮选**当前编辑第几小节**，按钮上实时显示「已有拍数 / 应有多少拍」
- 点音符按钮（全 / 二分 / 四分 / 八分 / 十六分）往当前小节追加
- **附点**和**休止**是**一次性修饰**：点完一个音符按钮就自动弹起，免得后面所有音符
  都被意外加上附点
- **退格**删掉当前小节最后一个音，**清空**清掉全部三小节

### 校验规则

时值统一以「四分音符 = 1」为单位，于是「一小节容量」只剩一条式子：

```
一小节容量 = 拍号分子 × (4 / 拍号分母)
4/4 → 4    3/4 → 3    6/8 → 3    2/2 → 4    3/8 → 1.5
```

| 小节 | 规则 |
|---|---|
| 第 1 小节 | **允许不足**（弱起 / pickup），只提示不算错；但**超出照样报错** |
| 第 2、3 小节 | **必须严丝合缝**等于一小节容量，多了少了都报错 |

第 1 小节「超出也报错」是有意的：把第 1 小节整个跳过听起来宽松，实际会放过一个装不下的
小节 —— 那不可能对应任何合法记谱，不是「弱起」能解释的。

出错的小节在两行谱上都会**标红**，下方提示会给出还差多少 / 超出多少拍。

### 两种记谱怎么对齐

小节**宽度统一由时值决定**（于是弱起小节自然就窄），两种记谱只在小节**内部**的排布
规则上不同：

- **五线谱**按**时值比例**排（真实记谱方式），音符落在各自时值格的中心
- **简谱**按**字符格**排：一个音符占 `1 + 破折号数` 格，全行等距

第一版让两者各算各的宽度，结果上下两行的小节线对不上，堆在一起非常乱。小节宽度是
**乐理信息**，不该由「用哪种记谱」决定。

简谱的下划线（八分 1 条、十六分 2 条）按「连续且该级都有的音符」**成组**画，而不是
每个音符各画一小段 —— 这样才像真的简谱。

### 谱子会存在本地

写的谱子和拍号会**自动存在这台设备的浏览器里**（`localStorage`），下次打开自动恢复，
界面上会提示「已恢复上次存在这台设备上的谱子」。点「清空」会连本地草稿一起清掉，
下次打开就是空的。

几条刻意的取舍：

| 决定 | 为什么 |
|---|---|
| **读回来的一律当不可信** | 用户可能手改过、可能是旧版本写的、可能被别的标签页写坏。校验不过就**整份丢掉用默认示例**，绝不"尽量修复" —— 畸形数据一旦进了应用，坏的是整套布局和校验逻辑 |
| **不认识的音值 id 要整份拒绝** | `makeNote` 遇到不认识的 id 会**悄悄退回四分音符**，于是"存的八分回来变四分"。这比直接丢掉严重得多 |
| **数值越界只夹住，不拒绝** | 音值合法就该收下；bpm 99999 夹到 400 就行，没必要因此丢掉用户写的谱子 |
| **格式带版本号** | 以后改了结构，旧数据要能被识别出来丢掉，而不是被误读成新格式 |
| **localStorage 不可用要静默降级** | 无痕模式、浏览器里禁掉、配额满 —— 任何一种都会让 `setItem` 抛异常。全部包在 try 里，失败就这次不存，绝不把应用搞崩 |
| **初始化时同步读，不能等 onMount** | 保存用的 `$effect` 会在 `onMount` **之前**先跑一次，那样就会拿默认示例把用户存的谱子**盖掉** |
| **防抖 300ms，但不在清理函数里撤销定时器** | 撤销了的话组件销毁时最后那一下改动就丢了。另外还监听了 `pagehide`，手机上切走前立刻落盘 |

内存里始终存**可直接使用**的 `RhythmNote`，打包成紧凑形式只发生在落盘那一刻 ——
"打包 / 解包"这对转换只待在一个地方。

### 记谱几何从哪来

`src/lib/notation/glyphs.ts` 改编自 `notation-perf/src/geometry.js`。没有直接引用那个
项目，是因为**产品不该依赖基准项目**（那边是实验代码，随时可能为了跑分而改动）。
代价是两份拷贝，可以接受。

## 演奏检测与速度测算

点「检测起点」，程序会**按能量峰值跳跃找出每一次演奏的起点**，和上面输入的节奏对齐，
算出实际弹奏的速度。

三步：

```
能量读数序列
  └─ detectOnsets()    找起点时刻
       └─ expectedOnsets()  用户输入的节奏 -> 每个音应该在「第几拍」（休止符不算起点）
            └─ matchTempo()  对齐 -> BPM + 每个音弹早/弹晚了多少
```

### 为什么全程在对数域（dB）里做

总能量的动态范围极大（实测中位数只有满量程的 3%）。用线性幅度判断「跳变」会被响度带偏 ——
**轻弹的一段一个起点都检不出来**。转成相对峰值的 dB 之后，「跳了多少 dB」对强弱基本免疫。
自检里专门有一条：一个很轻的音（幅度 0.02，约 -34dB）跟在满量程强音后面，必须也能检出来。

### 标准音与音高频率表

界面上「音高频率表」按 **A4 = 440 Hz** 的十二平均律，列出所选乐器音域内每个半音的频率
（每个半音 ×2^(1/12)，每个八度 ×2）。常见乐器的音域在 `src/lib/noteBands.ts` 里：

| 乐器 | 音域 | 乐器 | 音域 |
|---|---|---|---|
| 钢琴 | A0–C8 | 长笛 | C4–D7 |
| 吉他 | E2–E6 | 小号 | E3–C6 |
| 贝斯 | E1–G4 | 二胡 | D4–A6 |
| 小提琴 | G3–G7 | 竹笛 | A3–A6 |
| 大提琴 | C2–A5 | 古筝 | D2–D7 |
| 人声 | E2–C6 | 琵琶 | A2–E6 |

选一个乐器会**把检测范围限制在它的音域内**，能明显减少误检（贝斯手不该被高频噪声干扰）。
频带本身按**全音域**记录，所以换个乐器重测**不用重录**。

### ⚠️ 一个物理限制：低频分不出半音

能不能「一个半音一条带」由 FFT 分辨率决定，不由程序决定：

```
一个半音的间隔 = f × (2^(1/12) − 1) ≈ f × 5.95%
一个 bin 的宽度 = 采样率 / FFT 长度 = 48000 / 2048 ≈ 23.4 Hz
```

| 音 | 频率 | 半音间隔 | 能否分辨 |
|---|---|---|---|
| A5 | 880 Hz | 52 Hz | ✅ 远大于一个 bin |
| A4 | 440 Hz | 26 Hz | ⚠️ 勉强 |
| C4 | 262 Hz | 16 Hz | ❌ 不到一个 bin |
| E2 | 82 Hz | 4.9 Hz | ❌ 差得远 |

所以 `buildBands()` 会把**归属同一个 bin 的相邻音合并成一条带**，标签写成 `C2–D2` 这样的范围。
低音区只能给到音组、给不到单音 —— 这是信息不足，不是 bug。加大 FFT 能改善，但会牺牲时间分辨率。

> 建带这一步踩过一个坑：第一版拿「音的频率边界四舍五入」去定 bin 区间，结果 82.4Hz 的 E2
> 被标成了 `F2–G#2`，**差了整整两个半音** —— 因为一个音比一个 bin 还窄时，算出来的区间
> 整个落到了邻居的 bin 上。现在改成「每个半音归属**最近的 bin**，共用同一个 bin 的音合并」。
> 自检里有一条断言专门盯这个：880Hz 必须精确落到 A5 带上，82.4Hz 必须落在**覆盖 E2 的**带上。

### 循环折叠检测（真正管用的那一条）

前面所有单帧判据都在同一个坑里翻车，原因最后才看清楚：**需要的信息是跨时间积分出来的。**

一段练习录音里同一段会反复弹。真起音在每一遍的**同一相位**上出现；而泛音拍频
（弦有劲度，高次泛音不是严格整数倍，于是彼此拍频）的相位由琴弦物理性质决定、
和弹奏无关，每遍都不同。所以：

> 把能量包络按"一遍的时长"**折叠、跨遍平均** —— 真事件叠加保留，
> 拍频按 1/√N 衰减掉。

实测某段 26 秒的真实录音（周期 6.74s、弹了 3 遍半）：

| 方法 | 检出 |
|---|---|
| 最好的单帧判据 | 90 个起点（实际 27 个）|
| **折叠平均** | **9 个事件 × 3 个完整遍 = 27 个** ✓ |

折叠后峰谷差 15~21dB，谷底到 -23dB —— 那些相位上乐器根本没在响，
这是单帧判据永远看不到的结构。

**代价（必须记住）**：要求同一段**至少弹 2 遍完整**。只弹一遍用不了，
这时界面会提示并自动退回普通检测。

代码在 `src/lib/loop.ts`，界面在「演奏检测」里的「循环折叠检测」勾选框，
周期填 0 会从数据里自动估。

### 只用各频带的能量，不看总能量

第一版是"总能量 + 各频带"两路并用。后来去掉了总能量，理由是反直觉但很实在的：

> **底噪是摊在全部 ~80 条频带上的，而一个音只占其中一两条。**
> 所以单条带里的信噪比比总能量高出十几 dB —— **总能量恰恰是最容易被底噪推动的那个量。**

宽频的咔哒声、按键声、衣服摩擦，在总能量上都是一个漂亮的"峰值跳跃"，但在单条带上
什么都算不上。

代价是失去了"多个带同时起来时也能触发"这个能力（和弦、宽频打击）。补法是靠
**各条带分别报、再按时间合并**：同时起来的带天然会并成同一个起点，而且
`bandCount` 还顺带告诉你这一下有几条带参与（单音 vs 和弦 vs 宽频打击）。

实测对比（19 秒合成录音，9 个音 + 开头一声故意放的杂音）：

| | 总能量 + 频带 | **只用频带** |
|---|---|---|
| 检出起点 | 10 | **10** |
| 匹配 | 9/9 | **9/9** |
| 实测速度 | 95.97 BPM | **95.85 BPM**（真值 96） |
| 平均偏差 | 1 ms | **6 ms** |

质量没有下降，而抗底噪的余量变大了。注意 `detectOnsets()`（总能量那一路）**仍然保留**
并继续有测试覆盖 —— 它作为独立工具还有用（调试、对比），只是不再参与检测。

### 锚点不能死认第一个检测点

最初的做法是假设"第一个检测点就是第一个音"，在此基础上扫 BPM。这个假设很脆：
**只要开头有一声杂音被误检成起点，整段拟合就会按它对齐**，真正的第一个音被推到后面的
期望音符上。用户实测报的现象是「2 秒弹的第一个音被标成了第 2 小节」——正是这个。

现在把**前 40 个检测点各当一次锚点试一遍**，取评分最高的。靠后的点当锚点会让前面的
期望音全部落空、recall 暴跌，评分自然淘汰它们，所以不需要额外的启发式。

自检里有一条直接盯着这个：开头 0.3s 放一声杂音、真正的第一个音在 2.0s，
要求拟合出的 offset 必须落在 2.0s 附近（同时验证"只用第一个锚点时会偏 >0.5s"，
否则这条测试没验到东西）。

### 起点检测怎么做

| 步骤 | 做法 | 为什么 |
|---|---|---|
| 转 dB | 相对整段峰值取 `10·log10`，压到 -45dB 地板 | 对强弱免疫 |
| novelty | **只保留上升沿**（半波整流的一阶差分） | 「峰值跳跃」要的就是上升，下降沿是衰减不是起音 |
| 自适应阈值 | 局部均值 + `k` × 局部标准差（窗口 0.3s） | 固定阈值在轻/响段落里必然一头失灵；用前缀和压到 O(n) |
| 峰选 | 局部极大 + 过阈值 + 过绝对下限（1.2dB/帧） | 三重条件，缺一个都会误检 |
| 抛物线插值 | 用峰值和左右邻居拟合顶点 | 一个 hop 是 10.7ms，插值把这层量化误差压掉 |
| 最小间隔 | 70ms 内只留更强的那一下 | 防止一个音的起音被拆成两个 |

### ⚠️ 底噪被当成起点 —— 只有实测才能发现的问题

第一版在真实麦克风上会**把底噪报成几十个起点**。自检完全没抓到，因为测试里的"底噪"
用的是恒定值和缓慢正弦 —— 恒定值不产生 novelty，正弦的 novelty 极小，两者都恰好绕过了
这个 bug。**真实底噪是尖刺状的随机起伏。**

根因是判据本身错了：

> 自适应阈值是**从 novelty 自己的统计量**算出来的（局部均值 + k × 标准差）。
> 底噪永远在产生 novelty，所以"用底噪算出来的阈值"必然被底噪自己突破。
> 而绝对下限 `minJumpDb` 只有 1.2dB —— 底噪随便抖一下就 2~3dB。

修法是补一条**本质判据**：**毛刺是一根针，音符是一段台阶。**

| 判据 | 做什么 | 为什么 |
|---|---|---|
| **撑住检查** | 起音之后一整段的平均电平，必须仍比起音前高 | 底噪毛刺过一会儿就掉回原处，音符不会 |
| **抖动自适应** | 上面的"高多少"要大于**本底抖动**的 3 倍 | 固定阈值区分不了"轻声"和"底噪"：定 3dB 误杀轻声，定 2dB 底噪漏一片 |
| **用差分估抖动** | 抖动 = **相邻帧差分**的标准差，不是电平的标准差 | 一个音的**衰减**是"电平大幅变化但逐帧很平滑"，用电平标准差会把它当成巨大抖动，把紧随其后的下一个音误杀（实测：间隔 200ms 的两个音，第二个被拒） |
| **历史不够用全局** | 录音最开头没有足够历史估局部抖动时，退回整段抖动 | 只有一两个样本时标准差会估成 0，门槛直接塌掉。实测纯底噪在 t=0.02s 就是这么漏进来的 |
| **结尾不许放行** | 往后看不到时退化成电平检查 | 原来的"看不到就直接放行"等于在录音末尾开了一个洞 |

调试是一步步逼出来的，每一步都靠自检里那条**纯底噪必须零误检**的断言量：

```
40 个假起点
  → 加单点撑住检查            0 个，但误杀了"总能量只涨 3dB"的真实轻声
  → 改成一段平均              底噪漏 14 个
  → 加抖动自适应              5 个
  → 拉长抖动窗口              误杀间隔 200ms 的音（严重回归）
  → 改用差分估抖动            底噪 0 个，但开头漏 1 个
  → 历史不够用全局 + 结尾收紧  全过 ✓
```

同一套算法**在每条音带上各跑一遍**（阈值更高，默认 4dB，否则安静的带里一点噪声都在报），
再把结果和总能量的起点按时间合并。

### 音名是怎么定出来的

对每个起点，比较「起点之后 120ms」和「起点之前 120ms」每条带的平均 dB，差值 ≥ 4dB 的算
「这条带起来了」（紧贴起点的那 20ms 跳过 —— 那是起音过程本身，算进去所有带都会抬高）。
按抬升量排序，最强的作为**主音**，其余作为**其它音**一并报出来。

**不硬猜基频**：泛音强的乐器（某些拨弦、铜管）里，第二泛音可能比基频还亮，
这时主音会标成泛音的音名。所以界面上主音和其余音都显示，而不是只给一个数。

### 录下来回放，边听边看结果

点「开始」之后，麦克风的声音会**同时**录一份（`MediaRecorder`，opus 压缩）。
停麦后录音出现在「演奏检测」里，直接用原生播放器放 —— 这样测的时候可以一边听、
一边对照上面标出的起点和音名，不用反复弹同一段。

为什么用 MediaRecorder 而不是自己存 PCM：

| | MediaRecorder | 自己存 PCM |
|---|---|---|
| 一分钟 | 约 **1 MB** | 11 MB |
| 播放控件 | `<audio>` 原生，手机上就是系统控件 | 得自己写一套 |
| 和分析并存 | 同一条 MediaStream 分别喂两边，互不干扰 | 同样 |

录音会**自动存进 IndexedDB**（不是 localStorage —— 那个只能存字符串、还有 5MB 上限、
写的时候卡主线程），刷新页面 / 关掉重开都还在。旁边有「下载录音」，可以导出来。

**⚠️ 回放头必须减掉分析延迟。** 分析链路整体延迟 `delaySeconds` 秒（默认 1 秒），
所以界面上的第 t 秒，内容其实是第 t − delay 秒采到的。反过来算：录音播到第 p 秒时，
图上该停在 `p + delay`。**不减这个偏移的话，听到的和看到的永远差一秒**，就没法用眼睛对拍子了。

（`playheadAt()` 只有一行，但它决定了这个功能到底有没有用。）

停麦的顺序也有讲究：**必须先停录音再停音轨** —— 反过来的话最后那一小段会被截掉。

### 实测速度要同步过去，谱面才对得上

「能量记录」里的那个 BPM 和检测**没有关系**。实测速度是在 40~240 BPM 里全局搜一遍、
从演奏本身拟合出来的，跟上面标多少无关。

但**谱面分小节用的是上面那个 BPM**。两者不一致时，谱面上的小节线会整体错位 ——
你弹 96、上面写 120，小节线当然对不上。这时候光报一个「实测 95.4 BPM」是不够的，
用户还得自己手动去改滑块。

所以检测结果里会**明确标出不一致**，并给一个「用实测速度」按钮，点一下就把上面那个 BPM
换成实测值，谱面随即按实际演奏分小节。一致时则显示绿色的确认，不打扰。

### 速度怎么算出来的

**不是**直接对「时刻 ↔ 拍位」做一次线性回归 —— 那要求检测点和音符**一一对应**，
多打一下或者漏掉一个音，回归结果就整个偏掉。这里分两步：

1. **锚定 + 网格搜索**：假设第一个检测点就是第一个音（人总是从头开始弹），
   在此前提下从 40 扫到 240 BPM，取 F1 最高的那个
2. **最小二乘再拟合**：在匹配对上重新拟合斜率和截距，把网格的粗粒度补掉

容差跟着速度走：`0.3 × 最短音间距 × 每拍秒数`，再夹到 35~150ms —— 音越密，允许的绝对
偏差越小。

### 界面上那几个数字是什么意思

- **测得速度**：拟合出的斜率换算成 BPM
- **对上音符** `m / k`：k 是你输入的节奏里的音符数（休止符不算），m 是匹配上的
- **平均 / 最大偏差**：匹配上的音，实际时刻和拟合位置的差。**这个比 BPM 更能说明问题** ——
  BPM 相同但偏差很大，说明弹得忽快忽慢
- **多打**：检测到了、但没有对应音符的起点（多打或误检）
- **F1**：precision 和 recall 的调和平均。漏音拉低 recall，多打拉低 precision

### 结果按小节分行显示

结果**按小节分行**，每行 2 个小节（3 个小节就是「第 1-2 小节」+「第 3 小节」两行）。

不画成一条长轴，是因为检测的目的就是「和上面输入的节奏对照」，而节奏是按小节组织的。
分行之后每行自带小节线，和上面的谱面对照就知道是哪个小节、哪个音错了；一条长轴上只能
看出"这里错了一下"，说不出是第几小节。

**行宽按小节数成比例**，不拉满：3 个小节分两行时第二行只有 1 个小节，宽度就是第一行的
一半。这样所有行共用同一个时间尺度 —— 拉伸成等宽的话，第二行的能量曲线看起来会完全
不一样，反而误导。

小节边界用**三重手段**标示：交替底色 + 明显的小节线 + 行末终止线。
（第一版只有 30% 不透明度的灰线，在深色底上几乎看不见 —— 小节边界是这张图的骨架，
不该让人去找。）

每行左侧的「能量 / 检测 / 期望」三行分别是：dB 归一化后的能量曲线、检测到的演奏起点、
按测得速度推算的节拍位置。

| 元素 | 含义 |
|---|---|
| 蓝色面积 | dB 归一化后的能量曲线（按像素列取最大值，缩小时不丢瞬态） |
| 小节底色 | 同一行内相邻小节**交替深浅**，不靠线也能看出小节从哪分 |
| 小节线 | 明显的小节分界线，行末是**细+粗的终止线**（和真实记谱一致） |
| 小节号 | 标在每条小节线右侧（1 / 2 / 3），两小节一行时不用数 |
| 黄线 | 检测到的演奏起点 |
| 绿线 | 按测得速度推算的节拍位置 |
| 红线 | 该弹但没弹出来的音 |
| 粉色三角 | 多打或误检的起点 |
| 绿→黄斜线 | 那个音弹早/弹晚了多少 |

### 已知的局限（都有意留着）

- **依赖第一个检测点**：如果开头有一声杂音被检成起点，整体会偏移。目前没有做"哪个检测点
  才是第一个音"的搜索。
- **漏音太多会速度歧义**：全是四分音符时，若漏掉一半，BPM 可能被判成两倍/一半。
  F1 里的 recall 项能压住一部分，但漏得太多就无解 —— 这是信息不足，不是 bug。
- **连奏检不出来**：音与音之间没有明显起音（比如拉弦不换弓），就没有"跳跃"可检。
  这是能量法的固有边界，要解决得上谱通量或高频细节。
- **一次性分析**：点一次算一次，不做实时跟踪。改完上面的节奏再点一次即可。

### 对真实录音跑检测（不用开浏览器）

在应用里点「下载录音」，把文件放进 `samples/`，然后：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\detect-file.ps1 samples\你的录音.webm
powershell ... -File tools\detect-file.ps1 samples\你的录音.webm "q|qqqq|hqee"
```

> ⚠️ **无头 Chrome 的 `decodeAudioData` 是间歇性的**：有时永远不 resolve，页面打印完文件大小
> 就没下文了。这是 Chrome 音频服务的问题，不是代码问题（一个只有 fetch + decode 的最小探针
> 会以同样方式卡住）。所以脚本内部**自动重试 4 次**。

它走的是**应用自己的** `analyseAudioBuffer -> detectOnsetsWithNotes -> matchTempo`，
不是另写一套，所以在命令行看到的行为就是在浏览器里看到的行为。输出包含：总能量轮廓、
每个起点的时刻 / 音名 / 抬升 / 来自哪条判据、实测速度、匹配情况、逐音早晚。

节奏串：`q` 四分、`e` 八分、`s` 十六分、`h` 二分、`w` 全音符；大写是休止；
后面跟 `.` 是附点；`|` 分小节。

> ⚠️ **这个 .ps1 必须保持纯 ASCII。** Windows PowerShell 5.1 会把无 BOM 的 .ps1 按 ANSI 读，
> 中文注释会被拆散、甚至吃掉换行符，`param(` 块直接解析失败。这个坑在
> `notation-perf/bench/run-bench.ps1` 里记过一次，写这个脚本时又踩了一遍。

仓里带了一段合成录音 `samples/synth-19s.wav` 当基准：19 秒、96 BPM、底噪 -62dB、
9 个音（A4 C5 E5 G5 A5 C6 E6 G6 A6），外加开头故意放的一声杂音。当前结果是
**9/9 全中、实测 95.97 BPM（真值 96）、第一个音 1.972s（真值 2.000s）、平均偏差 1ms**。
改完任何东西先跑它 —— 数字不对就是回归了。

```bash
npm run check                  # svelte-check + tsc 类型检查

node tools/check-spectrum.mjs  # FFT 定位 / 频率映射 / 上色 / 能量 / 纵轴刻度
node tools/check-score.mjs     # 读数日志 / 小节换算 / 行边界 / 谱面几何
node tools/check-audiofile.mjs # 文件分析：列数 / 栅格 / 频率落点 / 压缩 / 取消 / 报错
node tools/check-rhythm.mjs    # 节奏模型：拍号容量 / 附点 / 弱起 / 严格校验 / 换拍号
node tools/check-notation.mjs  # 记谱布局：五线谱比例 / 简谱字符格 / 弱起 / 空小节
node tools/check-onset.mjs     # 起点检测：漏音 / 多打 / 抖动 / 锚点 / 80 条带底噪零误检
node tools/check-notes.mjs     # 音高与频带：十二平均律 / 音名 / 乐器音域 / 分辨率合并
node tools/check-draft.mjs     # 草稿存储：往返 / 垃圾输入拒绝 / 未知音值拒绝 / 存储不可用降级
node tools/check-recorder.mjs  # 录音：格式优先级 / 全不支持兜底 / 无 MediaRecorder 降级
npm run build                  # 生产构建
node tools/preview-spectrum.mjs  # 离线预览：合成音频 → 三张 PNG
```

`check-spectrum` 里有一条关键断言：给一个 3kHz 满量程正弦，峰值必须正好落在
第 64 个 bin 上，且幅度归一化到 1.0 —— 这能一次性验出 FFT、加窗和幅度缩放
三处是否都对。另外几条验证能量柱：能量越大柱顶越高、超出满量程夹在面板顶部、
面板以上的行一根像素都不许动（这保证它不会和频谱图串行）。

`check-score` 盯的是两件容易出错的事：**行边界不累积舍入误差**（连排 2000 行，
每行起点必须等于上一行终点），以及**`valueAtLevel` 必须是 `applyScale` 的逆**
（否则面板上标的刻度值就是在骗人）。

`check-rhythm` 盯的是需求里那条最容易做错的规则：**第 1 小节允许不足（弱起），但超出
必须报错**，而第 2、3 小节必须严丝合缝。同一个输入换个拍号，对错判定也要跟着变。

`check-notation` 只测**纯布局数学**（落笔部分依赖 `Path2D`，node 里跑不了，靠浏览器
截图验证）。关键断言：小节线必须铺满且首尾相接不重叠、音符落在各自时值格的中心、
空小节不能算出 0 宽或 NaN、`rhythm.ts` 用到的每个 glyph 都必须存在且路径串里没有 NaN。

`check-recorder` 能测的只有两件事 —— MediaRecorder 本身在 node 里不存在：
**格式挑选**（纯逻辑，要按优先级挑、要能兜住"一个都不支持"和 isSupported 抛异常），
以及**浏览器不支持录音时整个类要静默降级**（start 返回 false 而不是抛，stop/clear 能安全调用）。
真正的录音回放只能在浏览器里验证。

`check-draft` 的价值全在边界情况上 —— 正常存取谁都不会错，错的是"存坏了怎么办"。
所以断言几乎都在喂垃圾数据（空串、非 JSON、旧版本号、缺字段、未知音值 id、NaN、
越界数值、会抛异常的存储），要求它一律安全拒绝或安全降级、绝不把畸形数据放进应用。

`check-notes` 盯的是**换算精度**和**分辨率限制是否被如实反映**：440Hz 必须是 A4、
八度必须正好翻倍、半音必须是 2^(1/12)、几个必须背下来的频率（A0=27.5、C4=261.6、
A5=880、C8=4186）都要对到 0.01Hz；同时断言低频区**必须**出现合并带、A5 **必须**不被合并、
FFT 加大后合并带必须变少。

`check-onset` 里有一条**纯底噪必须零误检**的断言，是用户实测报错后补的回归测试 ——
它现在是整个项目里最有价值的一条断言，因为第一版的 40 个假起点只有它抓得住。

`check-onset` 是这个项目里最需要"防自欺"的一块，因为它全是数值逻辑，最容易看着对、
其实差一点。所以断言都带明确容差，并且专门构造真实演奏里一定会出现的情况：
**已知 BPM 必须恢复出来**（60/90/100/120/150/200 各测一遍）、**漏掉一个音不能让速度整个
偏掉**、**多打一下要被记进 extras 而不是被算成音符**、**带抖动的演奏平均偏差要落在抖动
幅度附近**、**恒定能量和缓慢起伏都不许检出假起点**、**轻弹的音跟在强音后面也要检出来**。

`check-audiofile` 不碰浏览器也不碰真实文件：用一个鸭子类型的假 AudioBuffer 跑完整的
离线分析。关键断言是**频率落点** —— 喂一个 1kHz 满量程纯音，栅格里最亮的那一行必须
正好是频率轴上 1kHz 对应的行；以及**压缩必须用最大值**（20 秒压到 200 列后纯音仍然亮）。

`preview-spectrum.mjs` 不接麦克风，用合成音频跑一遍完整的像素管线，写出三张 PNG：

- `tools/preview-spectrum.png` —— 实时两个面板（对数扫频 + 脉冲音 + 噪声脉冲）
- `tools/preview-score.png` —— 谱面视图（120BPM 4/4 的鼓点 + 和声，段落严格重复，
  所以图上每行的小节线应该和鼓点尖峰完全重合）
- `tools/preview-file.png` —— 整曲概览（40 秒、分成「前奏 / 主歌 / 副歌 / 尾奏」四段，
  走的是真实的文件分析链路，所以能量曲线上应该能一眼看出四个台阶）

改完渲染逻辑后不开浏览器就能看效果。

## 几个容易踩的点

- **worklet 必须独立成文件**：`ctx.audioWorklet.addModule('/wave-worklet.js')`，
  所以它放在 `public/` 下，不能被 Vite 打进主 bundle。
- **不能啸叫**：worklet 从不往 `outputs` 写数据，输出恒为静音；仍然连到
  `destination` 只是为了让音频线程拉取这个节点。
- **滚动而不是重画**：每帧只画新增的那几列，再把整块画布 `drawImage` 左移，
  这样每帧的像素写入量只跟新列数有关，与窗口大小无关。
- **切后台会落后**：`requestAnimationFrame` 在后台暂停，回来时可能积压了几千列；
  代码会直接丢弃旧列只画最新的，避免一次性补画把页面卡死。
- **改窗口大小会清屏**：画布尺寸变了，行→频率的映射也随之改变，旧像素不再对应
  正确的频率，所以直接清掉重画，几秒内会重新填满。
- **画布按设备像素渲染**：backing store = CSS 尺寸 × `devicePixelRatio`（封顶 2），
  绘制坐标**一律用设备像素**，且**不设变换矩阵**。
  这么定是被 `putImageData` 逼的：它**忽略变换矩阵、只认设备像素**，而画布里有三处。
  所以不能只改一半 —— 要么整体 CSS 像素（那就不能有变换），要么整体设备像素。
  `drawScore` 是唯一例外：它给文字设了 `setTransform(dpr,…)` 走 CSS 坐标（这样
  高分屏上文字才清晰），而能量行仍按设备像素 `putImageData`，两者互不干扰。
- **`score.ts` / `audioFile.ts` 里的导入要显式带 `.ts` 扩展名**：它们会被 node 直接
  加载来跑自检，而 node 的原生类型剥离不做扩展名补全。对应的 `tsconfig.app.json`
  里开了 `allowImportingTsExtensions`。Vite 侧两种写法都认。
- **文件能不能解码由浏览器说了算**：`decodeAudioData` 的格式支持是浏览器实现的，
  不是代码能决定的。`accept` 属性只是过滤器，真正兜底的是解码失败时的报错提示。
- **`start-dev.bat` 必须是 CRLF 行尾且纯 ASCII**：实测 cmd.exe 解析 LF-only 的
  批处理会错位（`echo` 整行消失、`ping` 的参数被当成命令执行），而 UTF-8 中文
  + `chcp 65001` 同样会被啃掉。所以这个文件是 CRLF + 英文提示，
  用编辑器改它时注意别把行尾转成 LF。
