# notation-perf —— 简谱 / 五线谱记号的渲染性能测试

回答一个很具体的问题：**"用浏览器自带能力画音符（简谱 + 五线谱，不同时值音符与休止符）" 和 "用图片拼接" 相比，性能差多少？**

结论摘要：**在实现质量对等的前提下，差距不大（同一数量级，约 1~2.5 倍）**；真正拉开差距的不是"矢量还是位图"，而是三件事：**网络请求数、像素总量(HiDPI/缩放)、DOM 节点数**。详见 [结论](#五结论) 与 [bench/results.md](bench/results.md)。

### 核心代码是什么

`src/geometry.js` 是全部画法共用的**唯一几何来源**：每个 glyph（全音符/二分/四分/八分/十六分/三十二分、附点、全休止到十六分休止）都用可序列化的路径命令定义在"线距(staff space)"坐标系里，原点 = 符头中心。

```js
var N = Notation.GLYPHS['eighth'];          // 八分音符 = 实心符头 + 符干 + 一条符尾
var d = N.toD(N.shapes[0].cmds);            // -> "M 0.62 0 C ... Z"
new Path2D(d);                              // Canvas 用同一份数据
'<path d="' + d + '"/>';                    // SVG 用同一份数据
```

这样做的意义：**SVG 与 Canvas 渲染出的形状逐点相同**，位图图集也是由同一份矢量光栅化而来，性能对比才不是"图形不同导致的假差异"。真实项目同样应保持"几何与渲染器分离"。

## 二、怎么跑

```powershell
# 单次基准（默认 2000 音符、6px/线距、dpr=1）
powershell -NoProfile -ExecutionPolicy Bypass -File bench\run-bench.ps1

# 高分屏（模拟手机/Retina）
powershell -NoProfile -ExecutionPolicy Bypass -File bench\run-bench.ps1 -N 2000 -Size 6 -Scale 2

# 长谱 + 密集谱面
powershell -NoProfile -ExecutionPolicy Bypass -File bench\run-bench.ps1 -N 8000 -Size 4 -PerRow 60
```

- 浏览器直接打开 `bench/bench.html?n=2000&size=6&perRow=50` 也能看表格。
- `demo.html` 用眼睛对照四种画法的实际效果（可拖动滑杆改谱面大小）。
- 注意：`chrome.exe` 是 GUI 子系统程序，用 `&` 调用既不等待也拿不到 stdout，脚本里用的是 `Start-Process -Wait -RedirectStandardOutput`；另外 Windows PowerShell 5.1 会把无 BOM 的 .ps1 按 ANSI 读，所以脚本内保持 ASCII。

### 测什么

| 指标 | 含义 |
|---|---|
| build / buildHot | 首次 / 热缓存下构建整谱的 JS 时间 |
| layout | 强制同步布局（`getBoundingClientRect`）耗时 —— DOM 方案的主要代价 |
| raster | Canvas 强制光栅化（`getImageData`）耗时 —— 位图/矢量像素成本的可测代理 |
| frameMs / rps | **整谱重绘**一次的平均耗时与每秒次数（模拟拖动/缩放时连续重绘） |
| nodes / heapMB | DOM 节点数 / JS 堆占用 |

## 四、怎么读这些数字（重要）

1. **DOM 方案的"绘制"成本没有被完整测量。** 无头 Chrome 里我能量到 DOM 的构建、样式/布局，但拿不到合成的绘制耗时；Canvas 的 `raster` 列是真实像素成本。粗略地讲，SVG/图片方案的真实总成本 ≈ 构建 + 布局 + 一次绘制（量级与 Canvas 的 raster 列相当，6~17ms/2000 音符）。所以上表中 DOM 的"整谱重绘"偏乐观，**结论方向不受影响，倍率会略微收窄**。
2. **图片方案用的是 data URL，网络成本被剥离。** 真实项目里"每记号一张图片"= 12 个 HTTP 请求（若按音符粒度或按符干方向/时值组合切片则几十个），弱网手机上首屏几百 ms 起；矢量或字体方案是 0~1 个请求。这是图片方案最大的一笔开销，且不体现在上表。
3. **单机单次测量有波动**（如 N=8000 时 Canvas 精灵的 raster 出现 1.7ms 的异常值），趋势比单点数值可信。
4. **手机与桌面差异主要在像素量与内存**：dpr=2/3 时位图要 2×/3× 图集，且缩放会重采样；矢量只需重新光栅化，天然清晰。这一点在 dpr=2 那组已经体现（精灵 29.8ms vs 矢量 21.9ms）。

## 五、结论

1. **矢量 vs 图片：差距不大。** 2000 音符、dpr=1 时，Canvas 矢量 10.4ms/次、CSS 雪碧图 10.3ms/次、Canvas 精灵 13.7ms/次、逐记号 PNG 18.1ms/次 —— 处于同一数量级，最好与最差约 1.8 倍。**"用图片会快一个数量级"并不成立。**
2. **真正的分水岭是这三个变量：**
   - **网络**：图片拼接必须先下载（且有解码成本）；矢量/字体无请求。
   - **像素总量 / HiDPI**：位图需多倍图集，缩放重采样；矢量无损。
   - **DOM 节点数**：SVG 每音符 2~4 个节点，8000 音符时 16001 节点、简谱文本方案 20915 节点，整谱重绘掉到 ~10 次/秒；Canvas 恒定 1 个节点，仍能 33~38 次/秒。
3. **Unicode 文本单次构建最快（0.1ms，250 次/秒整谱重绘）**，本机实测 Windows/Segoe UI Symbol 确实覆盖 U+1D15D、U+1D15F、U+1D13D；但安卓/iOS 系统字体是否带音乐字形不可靠，而且纯文本流无法把符头压到指定谱线上 —— 只适合做简谱或降级显示。
4. **选型建议**
   - **简谱**：文本 + CSS（下划线=时值、上下点=八度、`-`=延长、`0`=休止）足够；单屏数据量下 22 次/秒的重绘完全够用。要长谱顺滑滚动时，改用 Canvas 的 `fillText`。
   - **五线谱**：**Canvas 矢量自绘综合最优** —— 构建 4ms、整谱重绘 10ms、1 个 DOM 节点、零外部资源、任意缩放清晰。
   - **图片精灵**只在"倍率固定、资源已缓存、不做缩放"时才与矢量打平（CSS 雪碧图 10.3ms）；一旦 HiDPI 或用户缩放就要重建图集或忍受模糊。
   - 若把整页谱面**一次性离屏渲染成一张位图**再平移缩放（相当于把 Canvas 结果当图片用），那是最快的一档，但代价是缩放模糊 + 改动需整张重画。
   - **超过约 2000 个音符**，任何 DOM 方案都会先撞上布局/节点数瓶颈，应转向 Canvas + 视口裁剪 + 分层缓存。

## 六、修过的一个 HiDPI bug（2026-09）

`renderCssAtlas`（画法 E）原来只给元素设了 `background-position`，**没设 `background-size`**。
图集是按设备像素光栅化的（`unit = size × dpr`），元素尺寸也按 `1/dpr` 换算成了 CSS 像素，
唯独背景图仍按「1 图像像素 = 1 CSS 像素」显示 —— 于是取错了图集区域。

dpr=1 时两个量恰好抵消，所以只在 HiDPI 上暴露：实测 dpr=2 下三个音符只剩两根符干。

最小复现与截图留档：

- `bench/repro-css-atlas.html`
- `bench/repro-css-atlas-dpr1.png`（正常）、`bench/repro-css-atlas-dpr2.png`（修复后正常）

同时修掉的三处相关问题：

1. **图集缓存不随 DPR 失效**。浏览器缩放、或把窗口拖到不同 DPI 的显示器后，
   位图方案会一直用旧分辨率的图集。新增 `Renderers.watchDpr(cb)`（`src/render-canvas.js`），
   `demo.html` 已接上；`matchMedia('(resolution: Xdppx)')` 每次变化后重新注册。
2. **`sliceAtlas` 每次渲染都重新编码 N 张 PNG**（`toDataURL`）。`demo.html` 拖动滑杆时
   每格都要跑一遍。改为按图集缓存（WeakMap）。
3. **`window.resize` 不足以覆盖 DPR 变化**，所以第 1 条不能靠它。

⚠️ **这次也暴露了基准方法本身的一个盲区**：基准只测时间，测不出"画错了"。
cssAtlas 在只画出两根符干的状态下拿到了 11.59ms/86.3rps 的漂亮成绩，没有任何报错或变慢。
**视觉正确性必须靠 `demo.html` 或截图单独确认。**
